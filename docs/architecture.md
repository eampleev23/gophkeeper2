# Архитектура gophkeeper2

Менеджер паролей и зашифрованных данных с гарантией end-to-end шифрования: только пользователь может расшифровать свои данные. Сервер хранит только шифротексты и не имеет доступа к ключам.

---

## 1. Цели и границы

- **MVP:** пары логин/пароль + метаданные для навигации в интерфейсе. В будущем — произвольный текст, файлы (в т.ч. аудио/видео).
- **Платформа:** iOS (iPhone). Синхронизация только в рамках одного устройства; офлайн-режим с очередью изменений и синхронизацией при появлении сети.
- **Шаринг (позже):** передача доступа к записи другому пользователю только на чтение (read-only), с возможностью отзыва доступа.

---

## 2. Модель угроз

### Защищаемся от

| Угроза | Как достигается |
|--------|------------------|
| Компрометация сервера или БД | Сервер хранит только шифротексты. Ключи шифрования не покидают устройство пользователя (кроме зашифрованной обёртки DEK). |
| Прямой доступ к БД (в т.ч. разработчики) | Невозможно расшифровать данные без мастер-пароля пользователя. |
| Перехват трафика | TLS; полезная нагрузка уже зашифрована на клиенте. |
| Потеря/кража телефона без разблокировки | Данные на устройстве защищены ключом, привязанным к разблокировке (Keychain/Secure Enclave). Данные на сервере — шифротекст, ключ выводится из мастер-пароля, которого у злоумышленника нет. |
| Разблокированный телефон в руках злоумышленника, но без мастер-пароля | Просмотр записей в приложении требует ввода мастер-пароля; без него отображаются только метаданные (список), не секреты. |

### Вне рамок (не защищаемся)

- **Полная компрометация устройства (root / эксплойт):** при таком уровне доступа возможны перехват ввода мастер-пароля или извлечение ключа из памяти в «коротком окне». Считаем этот сценарий вне зоны ответственности приложения.
- **Социальная инженерия:** пользователь сам передал мастер-пароль или разблокировал устройство атакующему.

### Допущения

- Забытый мастер-пароль = безвозвратная потеря доступа к данным (восстановление не предусмотрено).
- Один устройство на пользователя в MVP; ключи не синхронизируются между устройствами через сервер.

---

## 3. Роль компонентов

- **Сервер (Go):** аутентификация (логин/пароль, JWT), хранение непрозрачных блобов (зашифрованные записи, зашифрованные ключи пользователя). Не выполняет шифрование/расшифрование пользовательских данных и не хранит мастер-пароль или DEK в открытом виде.
- **Клиент (iOS):** вывод ключей из мастер-пароля (KDF), шифрование/расшифрование данных, хранение ключей в памяти только на время сессии (с «коротким окном»), защита доступа к приложению через Face ID / passcode устройства.
- **Пользователь:** единственный, кто знает мастер-пароль; вводит его для просмотра каждой записи (или в рамках короткого окна — один раз на несколько просмотров).

---

## 4. Иерархия ключей

```
Мастер-пароль (MP)  ──[Argon2id]──►  Root Key (RK)
                                            │
                                            ├──► расшифровка DEK из блоба с сервера
                                            └──► (позже) расшифровка SK_user для шаринга

DEK (Data Encryption Key)  ──[AES-256-GCM]──►  шифрование записей (логин/пароль, текст, файлы)

Device Key (DK)  ──[опционально]──►  шифрование локального кэша на устройстве
                    (хранится в Keychain, разблокируется Face ID / passcode)
```

### Ключи

| Ключ | Где живёт | Назначение |
|------|-----------|------------|
| **MP** (Master Password) | Знает только пользователь, нигде не хранится. | Единственный секрет, вводимый пользователем. |
| **RK** (Root Key) | Выводится на устройстве из MP через Argon2id при каждом вводе пароля; не сохраняется. | Расшифровка DEK (и в будущем SK_user) из блоба, хранящегося на сервере. |
| **DEK** (Data Encryption Key) | На сервере — только в виде `Encrypt(RK, DEK)`. На устройстве — в памяти после ввода MP, в рамках «короткого окна». | Симметричное шифрование всех записей пользователя (логины/пароли, текст, файлы). |
| **DK** (Device Key) | Keychain (Secure Enclave), разблокируется Face ID / passcode. | Опционально: шифрование локальной копии данных для офлайн-режима; сервер его не видит. |
| **PK_user / SK_user** (будущее) | PK_user — на сервере в открытом виде. SK_user — на сервере только как `Encrypt(RK, SK_user)`. | Шаринг записей: выдача доступа другому пользователю без передачи мастер-пароля; отзыв доступа. |

### Алгоритмы

- **KDF (из пароля в RK):** Argon2id с достаточными параметрами (память, итерации) — одинаково на сервере для хэша входа в аккаунт и на клиенте для вывода RK (на клиенте — отдельный вызов Argon2id для RK).
- **Шифрование данных записей:** AES-256-GCM (нативный на iOS, CryptoKit). Nonce — уникальный на каждое шифрование (например, 12 байт random), никогда не повторяется с одним и тем же DEK.
- **Формат зашифрованного поля:** версия формата (1 байт) + nonce (12 байт) + ciphertext + tag (16 байт для GCM). Или явная структура (см. раздел 7).

## 5. Потоки пользователя

### 5.1 Регистрация (первый запуск)

1. Пользователь создаёт учётную запись (логин + пароль для входа на сервер).
2. Задаёт **мастер-пароль** приложения (для расшифровки записей).
3. Клиент:
   - по мастер-паролю строит RK = Argon2id(MP, salt_rand);
   - генерирует DEK (случайный симметричный ключ);
   - формирует блоб: `DEK_encrypted = AES-GCM(RK, DEK, nonce)` (+ сохраняет nonce/salt в блобе в явном виде);
   - (позже) генерирует пару PK_user, SK_user; сохраняет на сервере PK_user и `SK_user_encrypted = Encrypt(RK, SK_user)`.
4. Клиент отправляет на сервер: данные регистрации (логин/пароль входа) и после успешной регистрации — блоб с зашифрованным DEK (и при необходимости PK_user, SK_user_encrypted).
5. Сервер сохраняет блоб в записи пользователя, никогда не расшифровывает его.

### 5.2 Вход в приложение (логин)

1. Пользователь входит в аккаунт (логин + пароль входа) → получает JWT (cookie/токен).
2. Приложение может разблокироваться по Face ID / passcode (доступ к Keychain/экран приложения).
3. Для просмотра записей пользователь вводит **мастер-пароль**.
4. Клиент: RK = Argon2id(MP, …), запрашивает с сервера блоб с DEK_encrypted, расшифровывает DEK = Decrypt(RK, DEK_encrypted).
5. DEK хранится в памяти; начинается «короткое окно» (например, 30–60 секунд), в течение которого можно открывать записи без повторного ввода мастер-пароля.
6. По истечении окна или при уходе приложения в фон — DEK очищается из памяти; для следующего просмотра снова запрашивается мастер-пароль.

### 5.3 Просмотр записи

- Если DEK в памяти и окно активно — запись расшифровывается локально (данные уже могли быть загружены и закэшированы в зашифрованном виде).
- Если DEK нет — показывается запрос мастер-пароля → вывод RK → загрузка блоба DEK с сервера → расшифровка DEK → расшифровка записи.

### 5.4 Создание / редактирование записи

- Шифрование выполняется на клиенте: payload = структура записи (логин, пароль, заметки и т.д.), ciphertext = AES-GCM(DEK, payload, nonce).
- На сервер отправляется только ciphertext (+ метаданные для списка, см. раздел 6). Сервер сохраняет их без расшифровки.

### 5.5 Выход / смена пользователя

- Токен и DEK из памяти сбрасываются; при следующем входе снова потребуется мастер-пароль для расшифровки DEK.

## 6. Данные и метаданные (MVP)

### Что хранится на сервере

- **Пользователи (существующая таблица):** id, login, password_hash, salt, created_at, updated_at.
- **Ключевой блоб пользователя:** одна запись на пользователя — зашифрованный DEK (и в будущем PK_user, SK_user_encrypted). Формат блоба — на усмотрение клиента (версия, nonce, ciphertext, tag).
- **Записи хранилища (vault items):**
  - `id`, `user_id`, `type` (например, `login`), `updated_at`;
  - **Метаданные для списка (в открытом виде для MVP):** например, домен/название сервиса, чтобы строить список и поиск без расшифровки содержимого;
  - **Payload:** зашифрованный блоб (содержимое записи — логин, пароль, заметки — в зашифрованном виде).

Такой баланс даёт приемлемый UX (список, фильтрация, поиск по домену/названию) при высокой безопасности: сами секреты и пароли сервер не видит.

### Что шифруется на клиенте

- В payload записи (ciphertext): логин, пароль, заметки и другие чувствительные поля.
- Ключ DEK на сервере хранится только в обёртке Encrypt(RK, DEK).

### Офлайн-режим

- На устройстве хранится локальная зашифрованная копия (например, SQLite или файл с записями, зашифрованными DEK или DK).
- При отсутствии сети создание/редактирование пишется в локальную очередь; при появлении сети клиент синхронизирует изменения с сервером (отправка/получение зашифрованных записей и метаданных). Сервер не участвует в расшифровке.

## 7. Формат зашифрованных данных (соглашение клиент–сервер)

### Ключевой блоб (user keys)

- Назначение: хранить DEK_encrypted (и позже SK_user_encrypted) на сервере.
- Рекомендуемый формат (версия 1):
  - `version` (1 byte);
  - `salt` для Argon2id (если нужен для воспроизведения RK на клиенте — иначе salt хранится отдельно или фиксирован);
  - `nonce` (12 байт для AES-GCM);
  - `ciphertext` (DEK, 32 байта для AES-256);
  - `tag` (16 байт GCM).
- Сервер хранит блоб как непрозрачный BLOB; клиент при вводе MP вычисляет RK, запрашивает блоб, расшифровывает DEK.

### Запись хранилища (vault item payload)

- До шифрования (plaintext): структура, например JSON или бинарный формат — поля логин, пароль, заметки.
- Шифрование: AES-256-GCM(DEK, plaintext, nonce); на сервер отправляются nonce + ciphertext + tag (или упакованные в один blob с версией формата).
- Сервер не парсит payload, только сохраняет и отдаёт по запросу.

Конкретные форматы (байт-в-байт) можно зафиксировать в отдельном документе (например, `docs/encryption-format.md`) при реализации.

## 8. Будущее расширение

- **Шаринг (read-only + отзыв):** использование PK_user/SK_user и протокола выдачи доступа к записи другому пользователю без передачи мастер-пароля; механизм отзыва (аннулирование выданного ключа/доступа).
- **Смена мастер-пароля:** перешифрование DEK новым RK и обновление ключевого блоба на сервере; перешифрование записей не обязательно, если DEK не меняется (меняется только обёртка DEK).
- **Новые типы данных:** текст, файлы (аудио/видео) — тот же механизм: payload = произвольный blob, шифруется DEK на клиенте, сервер хранит ciphertext и метаданные по необходимости.
- **Шифрование метаданных списка:** при желании усилить конфиденциальность — шифровать и названия/типы на клиенте (тогда список можно строить только после расшифровки на устройстве).

## 9. Ссылки на реализацию

- Бэкенд: Go, Chi, PostgreSQL, JWT (текущий стек). Дополнительно: миграции для таблиц vault items и ключевого блоба; API для ключей и CRUD записей с зашифрованным payload.
- Клиент: iOS, CryptoKit (AES-GCM), Keychain, Argon2id (библиотека на клиенте для вывода RK). Логика «короткого окна» и запрос мастер-пароля — в клиенте.
